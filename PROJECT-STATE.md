**v75 / admin v2.9 — CHAT PERMISSION ERROR: real rules bug + a way to stop guessing:** Mohit reported "Chat unavailable: Missing or insufficient permissions". Two causes, both addressed. (1) **A genuine latent bug in the `msgs` rules.** They read `get(/tripchats/$(roomId)).data.members` with no existence check \u2014 and `get()` on a room that does not exist returns NULL, so `.data.members` fails and the entire rule evaluation errors out. Firebase surfaces that as "Missing or insufficient permissions", **which is indistinguishable from a genuine access denial** and is why this was hard to spot. Fixed with `roomExists()` checked FIRST so `&&` short-circuits before `get()` ever runs; verified the ordering is correct in the file. Also tightened create with a `text is string` type check. (2) **The bigger practical cause: rules are published by hand in the Firebase console and Mohit had not deployed the last few releases.** Rather than repeat "publish the rules" every session, built a way to know: new public-read `meta/rulesVersion` doc, `rwRulesCheck()` in the app which probes tripchats/staff/bans/pricing/meta and reports per-feature whether each is reachable or blocked, reachable by asking Tusk anything about "rules" or "permissions", and an **admin panel with a "I just published the rules" button** that records the version so the app can confirm currency instead of everyone guessing. (3) **Made the error message that users actually hit diagnostic.** The onSnapshot handler was still printing the raw Firebase string; it now detects permission-denied and says exactly what to do \u2014 paste firestore.rules in Firebase Console \u2192 Firestore \u2192 Rules \u2192 Publish \u2014 with a button to run the rules check. **LESSON: "Missing or insufficient permissions" is the least useful error in Firebase because a stale deployment and a real denial look identical; anywhere the app depends on hand-published rules needs a self-check, not a hope.**

Crypto payment is direct-wallet only (`CRYPTO_WALLETS`, empty = hidden), verified like UPI UTRs — no gateway, no fees.

**PWA (as of v31):** roamwise.co.in is an installable PWA. Files in repo root: `manifest.webmanifest`, `sw.js`, `icons/` (192/512/maskable-512/apple-touch-icon 180). Service worker strategy is deliberate — **network-first for HTML** (the app is one index.html that changes every deploy; cache-first would freeze installed users on an old build with no way to push fixes) and cache-first for static assets. Firebase/ads/geocoding/YouTube and `*.mp4` are never cached. Registration is guarded by `window.isSecureContext` so it never runs inside the APK's file:// origin, and install prompts are suppressed when the RW bridge or PLAY_MODE is present. To ship a breaking SW change, bump `VERSION` in sw.js (old caches are deleted on activate).

**Ads policy (as of v21): AdSense is WEBSITE-ONLY.** The loader in index.html detects the app (window.RW bridge OR PLAY_MODE) and never loads AdSense inside any app build — AdSense-for-Content in a native app violates AdSense program policy and endangers the whole account. Play Console declarations therefore: Advertising ID = **No** (manifest verifiably has no AD_ID permission, no ad SDKs); Contains ads = **No** for the app. Do not add play-services-ads / AdMob without revisiting both declarations.

## Known-fixed bugs (don't reintroduce)
1. **YouTube embed error 153 inside the app**: fixed by using the real YT IFrame Player API with `onStateChange` verification (checking for actual `PLAYING` state, not just `onReady`) — `onReady` can fire while YouTube silently shows its own in-frame error with no JS `onError` event. Falls back to native `RW.openExternal()` after ~4.5s if PLAYING never arrives.
2. **Pro survives logout**: was caused by an unsubscribed Firestore `onSnapshot` listener from a prior session firing a stale cached event after logout. Fixed by capturing and explicitly unsubscribing on sign-out, and making the signed-out auth branch authoritative.
3. **Missing `<uses-sdk>`**: causes "app not compatible" install failures on modern Android — always verify with `aapt2 dump badging <apk> | grep sdkVersion` after any manifest rebuild.
4. **Popular-card photo loading**: must be sequential (not parallel/burst), or the weserv.nl proxy rate-limits and some images silently never load.
5. **Journey Card canvas tainting**: any photo drawn onto the exportable card canvas must go through `fetchImg64()` (fetch→blob→dataURL), never a direct cross-origin `Image.src` — otherwise `toDataURL()` throws on save/share.
