# RoamWise 3.0 — six infrastructure enhancements
Status: repository code and review pipeline; remote resources and production acceptance are separate.

## Storage and media
Keep the isolated D1 database roamwise-knowledge-dev and private R2 bucket roamwise-public-media-dev. In Cloudflare dashboard create them only after reviewing account limits and billing. In GitHub Settings > Environments > knowledge-preview, configure RW_PREVIEW_D1_ID (the dedicated database UUID), CLOUDFLARE_ACCOUNT_ID and a narrowly scoped CLOUDFLARE_API_TOKEN secret. Do not paste tokens into a chat, PR or source. Configure environment reviewers if available. The workflow Deploy isolated RoamWise knowledge preview requires a manual main-branch run and the typed confirmation; it applies additive schemas and candidate SQL, and deploys only the preview reader. No production routes, changes to the main Worker, database deletion or DNS changes. Verify the selected D1 UUID/name and R2 bucket in the dashboard first. Review the execution output; check /health and an unpublished candidate returning 404. The preview cannot publish unreviewed candidates.

The weekly intake workflow prepares 226 India/international candidate destinations, source review packets, 226 Hindi itinerary scaffolds and Kumaoni/Garhwali native-review jobs. It checks at most 12 existing public reference URLs per week and records reachability only. HTTP success is not factual or licensing verification. No AI API, paid scraping, automatic approvals or public uploads. Human review is required for facts, source provenance, expiry, cultural context and all translated guides. Promote approved facts into the existing canonical tables only after recording reviewers and evidence.

For media add individual entries to knowledge/media-intake.json with id, destinationId, repo assets/ file, exact MIME type, SHA-256, rightsStatus, licenseProof, reviewer, reviewedAt, attribution and alt. The intake validator accepts images up to 4 MiB and videos up to 25 MiB, produces immutable private R2 keys, rejects unreviewed files and never uploads. For each reviewed entry, execute the explicit wrangler r2 object put command for that specific private bucket/key using --remote, --file and --content-type. Do not publish raw intake keys. Record rights and review in D1; the existing image schema/reader publishes only rights-approved image records linked to published destinations. Videos stay private in this phase; public video playback/range delivery and streaming costs require separate review. No asset is considered licensed merely because it is already in the repository. No approved photos or videos are supplied in this change.

After the reader is reviewed, bind it to the existing API Worker as the optional PUBLIC_KNOWLEDGE_READER service binding using Cloudflare dashboard. Without this binding the built-in atlas remains active. Deploy the production Worker only via the separate existing release procedure and verify auth/payment before and after. For public media, attach assets.roamwise.co.in to the dedicated reviewed reader, set PUBLIC_MEDIA_ORIGIN to that exact HTTPS origin, and recheck CORS, revoked destination media and the manifest. Homepage remote media lookup is optional and preserves the static fallback.

## Production acceptance (do not confuse tests with transactions)
- Live and preview HTTP/static parity monitor: check Actions artifacts and independently resolve both origins.
- On a real Android device and Chrome at 360/390/412px, open home, switch destinations (Almora/Tokyo/Nairobi/Funchal), use voice and all four itinerary modes, confirm the single wallet/settings controls, image fallbacks, accessibility and offline behavior. Record version, device, date, results and screenshots without user data.
- In Firebase console verify the two exact authorized domains; sign in using a test account on both, sign out and check session isolation. Do not record a token or customer data.
- In Cashfree merchant dashboard verify whitelisted domains, create/capture/refund a sandbox test order via the existing authenticated integration, verify server-side status and retries; no real payment is required. Record redacted evidence. Do not enable payment by changing DNS or copying keys.
- Review worker /tusk/search with localOnly=1 and queries for global atlas, unknown place, and a safe public query; verify a private-account query is blocked. Verify real /health and approved manifest only after staging setup.

## Failover
The separate public-browse-preview Worker implements a no-cookie, no-query, GET-only redirect to a healthy independent browsing origin for four allowlisted public paths. It does not proxy or fail over payments, auth, private pages, the main site or app. It is disabled by default, has no production route, does not follow redirects and rejects a self-loop or equal origins. Deploy and test it on a preview hostname only after confirming the backup origin actually serves independent content.

For full production active-passive failover use Cloudflare Load Balancing with independently healthy pools, origin host/SNI configuration, health monitors and a tested failback/rollback. It may incur additional charges. Confirm plan and budget in the dashboard; test failover with a staging hostname and real Firebase/Cashfree sandbox flows; do not attach production DNS until approval and acceptance. Existing GitHub Pages and Cloudflare Pages alone are not proof of independent origins. Do not configure the production domain as its own backend.
